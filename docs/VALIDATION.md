# PR 전 검증 기록 (2026-11-02)

작업 브랜치는 `codex/firestore-projects`입니다. 기존 미커밋 구현을 보존했습니다.
commit·push·PR·merge·실제 규칙 게시·Netlify 설정 변경·배포·유료 요금제 전환은 하지 않았습니다.

인증 세션과 OAuth 팝업은 사용자가 직접 검증해야 합니다. 이번 브라우저 저장 테스트의 계정은 실제 Google 계정이 아닌 Auth Emulator 계정입니다.

## 발견·수정한 문제

- 규칙 테스트가 compat 테스트 앱에서 Firestore를 다시 열면 별도 modular 인스턴스가 생겨 Emulator 연결을 잃었습니다. 저장소 생성 함수에 DB 공급 함수를 선택적으로 주입하게 하고, 테스트에서는 인증 토큰과 Emulator 주소가 설정된 정확한 DB를 재사용합니다. 기본 앱 동작은 동일합니다.
- 통합 테스트에 20초 제한을 추가해 잘못 연결됐을 때 무한 재시도를 방지했습니다.
- 규칙 거부 사례를 추가하고, 화면 렌더링 테스트는 실제 `.env.local`을 읽지 않도록 분리했습니다.
- 로컬 JDK·별도 설치 폴더와 Emulator 로그를 Git에서 제외했습니다.

규칙은 소유권, 최상위 문서 형태·설정·배열 크기·서버 시각을 검사합니다. 배열 안의 모든 블록·연결 항목을 서버 규칙에서 순회 검증하지는 않습니다.
블록별 값·ID 중복·연결 대상은 클라이언트의 저장/복원 검사에서 거부합니다. 본인 경로에 직접 조작한 중첩 데이터를 넣는 것까지 서버에서 완전히 막아야 한다면 후속 스키마/서버 검증 설계가 필요합니다.

## Node 조건의 정확한 의미

Firebase SDK 개발 저장소는 Node 24.12 이상을 요구합니다. 설치된 `@firebase/app`, `@firebase/auth`, `@firebase/firestore` 등 배포 패키지와 `@firebase/rules-unit-testing`에도 같은 engines 선언이 있어 SDK 자체 개발에만 해당한다고 말할 수는 없습니다.
그러나 이 앱은 Netlify에서 Node 서버로 실행되는 앱이 아니라 Vite로 만든 정적 파일을 브라우저에서 실행합니다.
브라우저 Firebase SDK에는 Node가 필요하지 않습니다. Node 22 빌드는 성공했고, 브라우저 entry가 선택되며 Node용 Firestore·gRPC는 묶이지 않았습니다.

Node 22 설치는 npm 기본 설정에서 경고 후 성공했습니다. `engine-strict=true`에서는 설치 실패 가능성이 있습니다.
현재 검증은 Node 22로 브라우저 앱을 빌드할 수 있다는 증거이며, Firebase Node SDK의 공식 Node 22 지원을 의미하지 않습니다.
배포 담당자는 Node 22 빌드 통과 사실과 엔진 경고를 함께 검토하고, 지원 선언을 맞추려면 팀 합의 후 Node 24.12 이상을 선택할 수 있습니다. 기존 `netlify.toml`은 수정하지 않았습니다.

근거: [Firebase 지원 환경](https://firebase.google.com/docs/web/environments-js-sdk), [공식 Firestore 패키지 선언](https://github.com/firebase/firebase-js-sdk/blob/main/packages/firestore/package.json).

## npm audit high 5개

실제 근본 패키지는 설치된 `@grpc/grpc-js@1.9.16`입니다. high 표시가 `@firebase/firestore`, `@firebase/firestore-compat`, `firebase`, 개발 전용 `@firebase/rules-unit-testing`으로 전파돼 5개로 집계됩니다.
독립적인 high 취약점 5개가 발견된 것은 아닙니다.

- high: 서버가 클라이언트 인증서를 필수로 요구하지 않는 특정 구성에서 `getAuthContext`를 인증에 이용하면 승인되지 않은 인증서를 승인된 것처럼 취급할 수 있습니다.
- 함께 연결된 low: gRPC 서버의 오류 처리기가 던진 오류 메시지가 클라이언트에 전달돼 민감한 정보가 노출될 수 있습니다.
- 둘 다 gRPC 서버 사용 조건이 핵심입니다. 현재 앱은 gRPC 서버를 만들지 않으며, 실제 브라우저 번들에 이 패키지가 포함되지 않는 것을 확인했습니다. 따라서 현재 정적 운영 앱에서 이 취약점의 실행 경로는 확인되지 않았습니다.
- 개발 도구만의 의존성은 아닙니다. Firebase Node 클라이언트 의존성에도 설치돼 있습니다. 향후 서버 코드·Functions·SSR을 추가할 때 다시 평가해야 합니다.
- 수정판은 1.13.6 또는 1.14.5 계열입니다. 다만 현재 Firestore가 요구하는 `~1.9.0` 범위를 벗어납니다. 범위 안 `npm update`만으로 해결되지 않습니다.
- 안전한 기본 경로는 상위 Firebase가 수정 의존성을 채택한 릴리스를 검토하고 테스트 후 적용하는 것입니다. 별도 scoped override는 가능하지만 상위 의존성의 요청 범위를 강제로 바꾸므로 이번에는 적용하지 않았습니다.
- `npm audit fix --force`가 제안한 Firebase 9로의 변경은 대규모 버전 변경이므로 실행하지 않았습니다. 무검증 override나 SDK 대규모 변경은 로그인·저장·Node 통합 테스트에 영향을 줄 수 있습니다.

근거: [high 공식 권고](https://github.com/advisories/GHSA-m9gg-hp2v-232j), [low 공식 권고](https://github.com/advisories/GHSA-f596-whhp-79r4).

## 실제 테스트를 이어갈 순서

1. Firebase 콘솔 규칙 탭의 기존 규칙을 보존·비교합니다. 프로젝트 저장 경로 이외 팀 기능이 있으면 함께 검토합니다.
2. 이번 규칙을 검토 후 게시합니다. 기존 공개 catch-all 규칙이 새 제한을 무력화하지 않는지 확인합니다.
3. 게시 완료를 알려준 뒤 `localhost`에서 실제 Google 로그인 상태를 확인합니다.
4. 본인 계정에서 이름이 명확한 테스트 프로젝트 1~2개만 새로 만들고 저장·수정·새로고침·불러오기를 검증합니다. 기존 팀원 문서는 건드리지 않습니다.
5. 두 번째 계정으로 목록 분리를 확인합니다. 테스트 문서 삭제는 MVP에서 허용하지 않으므로 별도 승인 없이 삭제하지 않습니다.

Emulator는 실제 Firebase 사용량을 발생시키지 않습니다. 실제 읽기 점검은 소량의 요청만 사용했고, 결제 연결·Blaze 전환은 하지 않았습니다.

## PR과 배포 담당자 전달 사항

검토용 PR을 준비할 수 있는 상태입니다. 실제 규칙 게시와 실제 계정 저장 검증은 운영 반영 전에 남은 확인 사항입니다.
팀원 1명 이상 Approve 후 PR 작성자가 merge하는 새 규칙을 따르되, 사용자의 명시적 승인 없이 merge/main push를 하지 않습니다.

배포 담당자에게는 다음을 전달합니다.

- 같은 Firebase 웹 앱의 환경변수 네 개를 빌드 범위·운영 환경에 등록한 뒤 새 빌드를 실행해야 합니다. 값은 문서·PR에 넣지 않습니다.
- Node 22.23.4 빌드는 성공했으나 Firebase engines 경고가 있습니다. strict 엔진 검사와 실제 배포 환경 버전을 확인해야 합니다.
- 운영 도메인은 승인됐으며, 임의의 Deploy Preview 주소는 자동 승인되지 않습니다.
- Firestore 규칙은 별도 적용 작업입니다. Netlify 배포만으로 `firestore.rules`가 게시되지 않습니다.
- 운영 번들에 Emulator 테스트 도구를 추가하지 않으며 유료 서비스가 필요하지 않습니다.
